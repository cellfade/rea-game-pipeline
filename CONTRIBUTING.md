# Contributing

Open a focused issue or PR describing the task, evidence, observed failure and proposed improvement. Include a small synthetic reproduction without private target data. Avoid adding universal rules from a single project unless the invariant generalizes.

Each PR should state behavior before/after, affected skill or contract, regression case, tests actually run, and remaining limitations. An independent reviewer checks the candidate against the original scenario and one unrelated holdout. Never change test expectations merely to hide a failed gate. Benchmark claims include task success and cost, not only output length.

Keep public examples synthetic, portable and credential-free. Run unittest, package validation, privacy scan and exact staged-tree review. Do not add client-specific paths, mandatory model choices, account names or deployment destinations. No silently downloaded prerequisites.

Use semantic versioning for the package; document schema and skill behavior changes. A breaking manifest change requires migration guidance. New providers require a real compatibility proof, not only a mocked tool response.
